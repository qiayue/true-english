# 项目规划

## 产品定义

**true-english 是一个基于真实推文的英文写作训练器。**

它不是阅读工具。核心动作是「回译 → 对答案 → 看 diff」：
学习者只看中文，凭中文把意思翻回英文，再和母语者原句逐处对比。
**diff 就是课程内容。**

方法论见 [method.md](method.md)。

## 三个指挥决定

**1. 素材管线排在最后，不排在最前。**
推文获取是全项目最不确定的一环（X API 要付费、爬虫违规且脆弱），
但它**不产生任何价值**。手动粘贴一条推文，整个系统照样跑通。
最不确定的东西不该卡住最有价值的东西。

**2. 先做 diff 引擎，它是成败点。**
如果批改质量不行，后面做多漂亮都白搭。所以第一件事是把它做成 CLI + eval 集，
先证明输出质量，再包装成产品。

**3. 批改必须三分：错 / 可以但不自然 / 一样好。**
同一个意思本来就有多种正确写法。全盘标红既让人崩溃，也不诚实。
这条是 prompt 里的硬约束，也是 eval 集里最关键的两条用例
（`equal-different-but-good` 和 `near-perfect`）。

## 关于难度打分器的一个设计结论

第一版用 OpenSubtitles 词频表，误杀了正常推文。原因值得记下来：

推文的**语域**是口语化的，但**话题词汇**是工作/软件/产品/想法 ——
电影对白语料覆盖不到。而且纯靠词频秩无法分离：
`productive` 秩 11269（学习者认识）和 `inflation` 秩 14466（未必认识）是交错的，
抬高阈值只会同时放进两者。

所以改成分层：通用词频表（粗筛）+ 领域补充词表（`data/freq/domain.txt`）。

**但真正正确的做法是按学习者本人来定。**
`ScoreOptions.extraKnown` 是为此留的接口：app 记录他实际点开查词的那些词，
反过来精修他的个人已知词集合。**难度过滤器应该学习这个人的词汇量，
而不是套一张固定表。** 这是 M3 要接上的。

## MVP 的几个设计结论

**零新增依赖。** 用 `node:sqlite` + `node:http` + 单文件前端，不上 Next.js。
这个阶段它是本地单人工具，上线需要的鉴权和多用户远超 MVP 范围；
核心逻辑都在 `src/core/`，与框架无关，将来换壳很便宜。

**服务端不下发英文原文。** `GET /api/cards/:id/practice` 只返回中文 gloss。
整套方法的价值全部来自「先产出，再看答案」—— 英文躺在 DOM 里，
偷看成本就是零，练习立刻退化成抄写。服务端不发，才是真的不发。

**导出批改请求时不落库。** 导出和导入之间用户可能中断（关页面、忘了贴回来）。
如果导出就写 attempt，那些永远等不到批改的孤儿记录会让「回译次数」
和重合度趋势全部虚高 —— 而这套系统最值钱的产出恰恰就是那份统计。
改成无状态：回译内容随导入请求一起回来，届时和批改结果原子写入。

**手工模式会校验批改是否串卡。** 同时开多张卡片、复制粘贴串行很容易发生，
串了之后系统会把 A 卡的错误算到 B 卡头上，污染错误模式统计。
判据是批改里引用的 native 片段应当出自本卡原文。

## 支架四级与排程

练习不是一种模式，是四级支架，**同一条推文每次只停在它当前该在的那一级**：

| 盒子 | 支架 | 做什么 |
|---|---|---|
| 新卡 / 0 | 照抄 | 看一眼 → 遮住 → 打出来 |
| 1 | 填空 | 只填你容易错的位置 |
| 2–3 | 逐句 | 只看中文，一句一句写 |
| 4+ | 整段 | 只看中文，整条连起来写 |

练成了升一格，下次自动少一层支架。**不是每天把四级走一遍** ——
四级 × 五步 × 重复，一条推文能磨掉一小时，而方法论写的是每天 25 分钟。

两条实现上的硬约束：

**照抄不能是「摆着让你抄」。** 抄写最大的风险是空转：眼睛在原文和输入框
之间来回弹，手在搬运，脑子没参与。所以必须先遮住再打，中间那个记忆缺口
才是这一级唯一有用的部分。

而「看」和「遮住」必须是**同一个界面的两个状态**，不是两个界面。
原来的实现三处都在动：输入框收起来又冒出来、答案卡换成一条矮一半的斜纹带、
提示从两行变成四个字 —— 于是按钮往上蹿一大截，看起来就是换了一屏，
而这一级要传达的其实是「同一句话，现在盖住了」。

改法：答案槽始终是同一个 `.card`，遮住时文字保留 `visibility:hidden`
（还占着位，高度分毫不变），斜纹罩在上面；输入框始终在原位，
该看的时候 `disabled`；提示行给定死的最小高度。
冒烟里因此有两条断言量的是**布局别动**：遮住前后答案槽高度差 < 2px、
主按钮 y 坐标差 < 4px。

顺带消掉了一类分支：「再看一眼」以前要判断刚才那里放的是原文还是对照结果、
各自重新渲染一遍（照抄级没有 diff，于是点了没反应 —— 那是第三次事故）。
现在盖上和揭开是同一个动作，不需要知道底下是什么。

**填空不能随机。** 随机挖掉 Cloudflare 只是在考拼写记忆。挖空点来自
批改结果里的 leak 统计 —— 你的冠词漏过，就挖冠词。整个系统因此自洽：
批改 → 错误统计 → 填空选点 → 再批改。

排程按**时间预算**而非条数：20 条复习同时到期是 SRS 用户流失的经典场景，
而条数不是负担的度量，时间才是（照抄两分钟，整段八分钟）。
权重除了逾期和盒子，还加了「这张卡能不能练到你当前最严重的漏点」。
超预算明说有积压，不默默截断。

## M9：把力气从手段挪回目的

做到 M8c 时，系统是瘸的。回译那一侧（**手段**）有四级支架、间隔重复、
批改引擎、提示阶梯、掌握循环 —— 一整套机器。仿写那一侧（**目的本身**）
只有一个输入框加一个子串计数器，零反馈；语料库只是一个能浏览的列表，零调度。

`grep -c "chunk.*box\|chunk_progress\|chunk.*due" src/core/store.ts` 返回 **0**。
六十个词块入了库，系统不知道你哪个用过、哪个用对过、哪个该再推给你。

M9 补的是一个环：

```
推今天该用的词块 → 他写 → 批改判定哪些**真的用对了**
                              → 更新词块熟悉度 → 明天推该用的给他
```

### 仿写批改为什么不能复用回译批改

回译有标准答案（原文），仿写没有 —— 他想说什么只有他知道。
所以仿写批改的第一产出不是「你错在哪」，而是
**「同样这个意思，一个母语者会怎么写」**。那个版本本身就是新的对照素材，
而且是关于他自己想说的话的，比任何现成材料都贴身。

产出顺序刻意是：母语者版 → 读懂了吗 → 逐处对比。
把语法排最后不是因为它不重要，是因为它不该抢占注意力：
**写作的第一目标是被读懂**。

`equal` 这一档在仿写里比回译更要紧：回译时原文是既定的，判 equal 还算克制；
仿写时连「标准答案」都是批改现编的，如果把所有不同于它的写法都标成问题，
那不是批改，是把批改器的文风强加给学习者。

### 「用对了」和「出现了」必须分开

字符串匹配到 `be about to`，可能是 `I be about to go`。
把这种算成复用成功，系统会把这个词块的复习间隔往后拉 ——
那个错从此再没人纠正。所以：

| 信号 | 来源 | 后果 |
|---|---|---|
| 匹配到 **且** 批改认了 | 机械匹配 ∩ `chunkUse` | 升一格 |
| 匹配到 **但** 批改没认 | 机械匹配 ＼ `chunkUse` | **打回第 0 格**（他以为自己会 —— 最强的信号） |
| 只匹配到，没批改 | 只有机械匹配 | 最多升到第 1 格，永远称不上「掌握」 |

界面上的实时提示因此说「碰到 3 个词块」，不说「复用了 3 个 ✓」——
后者会让人以为已经过关，而真正的判定在批改里。

### 漏点画像合并两个来源，但自由写作的按双倍计

回译时漏了个冠词，可能只是没记住原文那个位置有没有 the；
自己写句子时漏冠词，才说明这条规则根本没进脑子。
后者是真实写作水平，是这个项目的目标，权重理应更高 ——
填空级挖哪些空、排程给哪张卡加权，都吃这份画像。

### 写作台只有一份，它会搬家

仿写要紧接在批改后面（方法论：「当天必须用它说 3 件你自己的事，
不许『以后再用』」），但它也该有自己的标签页。
两处各放一个复制品的话，两份迟早各自漂移 —— 那正是前两次事故的成因。
所以整个应用只有一个 `#desk` 节点，它在练习页和写作页之间**移动**。

代价是三个新的静默故障：搬丢（写作页空白）、搬重（两个同 id 的输入框）、
搬家丢内容（正在写的推文没了）。都不会让原有断言变红，所以三条都有专门的断言。

## 两次同类事故，和它换来的检查

我两次用「从 X 替换到 Y」的大范围改写重写 JS，都没检查那个区间里还有什么：

1. 吞掉了 4 个按钮 handler 和 renderReview —— 按钮点了没反应
2. 吞掉了 3 行 let 声明 —— openCard 一进来就 ReferenceError，卡片打不开

两次都是**运行时才炸**：页面照常渲染、JS 语法照常通过、tsc 照常干净。
第一次是用户点了才发现，第二次是冒烟测试抓到的。

### 为什么补丁式的测试挡不住

前三次事故之后我每次都补一条断言，但事故照旧 —— 因为**测试是被动长出来的**：
用户报一个 bug，我补一条覆盖。于是它永远只覆盖「已经坏过」的路径，
从不覆盖「即将坏」的。照抄级的「再看一眼」点了没反应，就是这么漏出去的。

改成机械枚举：**从 HTML 里列出全部按钮，跑完断言每一个都被点过。**
点不到的必须在 EXEMPT 里写明理由，不能默默放过。
第一次开这个检查就抓出四个从没测过的按钮，其中 `btn-import-card`
是手工模式下每天必经的路径。

### 三道检查

```
npm run verify     # 自己起服务、自己收摊，不碰你的库
```

| | 命令 | 挡什么 |
|---|---|---|
| 静态 | `npm run check` | 按钮没接线、引用了不存在的元素、函数被删、变量被赋值但从未声明、TS 类型、全部单元测试 |
| 端到端 | `npm run smoke` | 75 项，覆盖每一条用户真的会走的路径 + **点击覆盖率断言** |
| 交互 | `npm run audit` | 横向溢出、重复提交、键盘走不通、空状态没提示、写作台会不会被搬丢 |

**只覆盖一半的测试比没有测试更危险** —— 它给人「测过了」的错觉。

审计里每条检查都必须是**行为验证**，不是静态查源码。为此返过两次工：

1. 第一次写成「查 handler 里有没有 disabled」，而防重是在 onclick 赋值处
   统一拦的，源码里根本看不到，于是全员误报。
2. 第二次是「整段模式有没有键盘提交」，正则带了 `s` 标志，
   `#attempt` 后面跨了几百行匹配到别处的 keydown —— **一直假绿**，
   明明没有快捷键，审计却说有。发现时才补上 ⌘/Ctrl+Enter。

**每加一条新检查，都要摘掉对应的实现确认它真的会红** —— 不会红的检查等于没有。

还有两个同类的坑，都是「静默地不测」：

- **跑不到的检查必须出声。** 审计里依赖卡片的几条，库为空时原本 `continue`
  掉了，于是空库上全绿。现在改成报错并说明怎么补数据。
- **崩了要给人话。** 断言失败会记进结果，但「元素等不到」是直接抛
  TimeoutError，顶层 await 里就是一坨堆栈，看不出断在哪一步 ——
  而「按钮不见了」正是这个脚本最该抓的那类回归。现在会打印
  「最后通过的是哪一条 / 等不到哪个选择器」。
  （钩子必须挂 `uncaughtException`：ESM 顶层 await 的 rejection 走这个，
  不走 `unhandledRejection`；而且挂了就等于吞异常，不显式 `exit(1)`
  的话崩溃会变成「通过」。）

`verify` 现在自己起一个 5174 端口 + 独立数据库的服务，跑完收摊。
以前它直接打 5173，等于每验收一次就往你自己的库里塞一张测试卡、
把练习进度搅乱，而且你开着 `npm run dev` 时没法验收。
